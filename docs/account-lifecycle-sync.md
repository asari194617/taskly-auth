# アカウント退会・消去の同期

## 目的

Taskly の退会状態と認証 DB のログイン可否を同じ利用者 ID で同期し、退会後に OAuth、パスキー、パスワード、メールコード、TOTP、復旧コードから再認証できないようにする。退会から30日後の消去では、認証 DB とアプリ DB のどちらにも利用者データを残さない。

## API

Taskly API と退会消去 DAG だけが、OAuth クライアント資格情報とは別の `AUTH_INTERNAL_TOKEN` を Bearer token として使用する。

### 退会

`PUT /internal/users/{id}/lifecycle`

```json
{
  "deleted": true,
  "deleted_at": "2026-09-24T00:00:00Z"
}
```

- `deleted` は `true` だけを受け付ける。認証情報を復活させる退会取消は提供しない。
- `deleted_at` は UTC の RFC 3339 とし、未来時刻は拒否する。
- 対象利用者を行ロックし、`is_deleted=1` と `deleted_at` を保存する。再送時に退会日時を後ろへ延ばさないよう、既存値と要求値の早い方を残す。
- 同じトランザクションで認証セッション、チャレンジ、WebAuthn セッション、OAuth 認可コードを削除し、アクセストークンとリフレッシュトークンを失効する。新旧メールコードを使用済みにし、移行済みの旧 Taskly セッションも削除する。
- 存在しない利用者は 404、同じ要求の再送は 200 とする。

Taskly はアプリ DB の退会処理を完了してからこの API を呼ぶ。同期に失敗した場合もアプリ側の退会とセッション失効は戻さず、呼び出し元へ同期保留を返す。OAuth コールバックはアプリ DB の `is_deleted` も確認するため、同期保留中に Taskly セッションは作成されない。運用担当者は同じ要求を再送する。

### 期限後消去

`DELETE /internal/users/{id}`

- 退会済みの利用者だけを受け付ける。未退会なら 409 とする。
- 認証サービスが保持するパスワード、パスキー、TOTP、復旧コード、ブロック、メールコード、セッション、チャレンジ、OAuth コードとトークン、利用者行を一つのトランザクションで削除する。
- 対象がすでに存在しない場合も再実行成功として 204 を返す。

退会消去 DAG は、認証 DB の消去が成功してからアプリ DB の消去トランザクションをコミットする。後段が失敗するとアプリ側の退会行が残るため、翌回は同じ DELETE を安全に再送できる。認証 DB の消去失敗時はアプリ DB を削除しない。

## 設定と段階導入

- 認証サービス: `AUTH_INTERNAL_TOKEN`
- Taskly API / Airflow: `AUTH_ACCOUNT_LIFECYCLE_EXTERNAL=1`, `AUTH_LIFECYCLE_SYNC_URL`, `AUTH_INTERNAL_TOKEN`
- フラグの既定値は `0` とし、開発環境では既存の単一 DB 動作を維持する。
- 本番では最終コピーと件数・ハッシュ照合後にだけ有効化する。Taskly API と Airflow に同じフラグ、URL、token を設定し、片方だけ有効にしない。
- `AUTH_LIFECYCLE_SYNC_URL` は HTTPS、または同一ホスト・private network 上の HTTP に限定する。redirect は追従しない。

## 障害、監視、復元

- internal API の 5xx は既存の汎用 Discord アラートへ送り、利用者 ID、メール、token、要求本文を通知に含めない。
- Taskly API は同期失敗をログとエラー監視へ送り、退会済み利用者を有効へ戻さない。
- Airflow は同期失敗で対象利用者の DB トランザクションを rollback し、DAG 失敗通知と次回実行で再試行する。
- バックアップ復元後は、バックアップ取得後の退会・消去台帳を両 DB に再適用する。認証 DB に利用者を復活させたまま外部公開しない。

## 切り替え確認

1. 存在しない利用者、認証失敗、不正 JSON、未来の `deleted_at` を拒否する。
2. 退会の再送で `deleted_at` が延びず、全セッションと OAuth token が利用不能になる。
3. 同期通信失敗後もアプリ側が退会状態を維持し、再送で収束する。
4. 期限前と保留中の利用者を消去しない。
5. 期限後は認証 DB を先に消去し、アプリ DB 失敗後の再実行でも完走する。
6. 隔離したバックアップから復元し、退会・消去の再適用後に件数だけを照合する。
